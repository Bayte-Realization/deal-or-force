# Распределение языков разработки — ответ на вопрос, 27 октября 2026

Вопрос: какие аспекты игры под какие поддерживаемые языки отдать, чтобы выжать
максимум производительности, читаемости, модифицируемости и минимум потребления
ресурсов. Рамки от пользователя: **29 октября 2026 вето на Rust снято**; Kotlin можно, но
BTA-мод забыть; переводить код игры на другие языки там, где надо.

## Короткий ответ

**Основной язык остаётся C#.** Измеренные эксперименты (см.
`LANGUAGE_KERNEL_NOTE_2026_10_24.md`) пока не обосновали включение конкретного
native-backend: Ownership-BFS на Odin/Rust проиграл медиану C# и хук снят.
Это результат определённых алгоритмов, входов и границы вызова, **не доказательство**,
что любой код на другом языке бесполезен или что будущий пакетный kernel не ускорит
игру. Читаемость, модифицируемость и проверяемость — самостоятельные причины переноса.

Актуальная инвентаризация: C#/GDScript в Godot, девять дополнительных треков
LanguageKit — Luau, F#, Nim, Odin, Kotlin и Rust (все шесть проверены ранее; вето на
Rust снято 29 октября) плюс Zig, Go и Python (написаны, на 4.8-beta2 не запускались).
Lua и Godot Sandbox — отдельные опциональные адаптеры, не Luau.
Адаптер/лаборатория не равны включённому игровому backend. Игра на .NET 10,
общая F#-библиотека и standalone-стенды таргетируют .NET 8; F# SDK игроку не нужен.
Сейчас в производственной F#-сборке семь файлов правил: AssaultRules, CatalogueWindow,
WarScoreRules, PeaceRules, CombatTempoRules, DiplomaticActRules, PoliticalPolicyRules.
Датированные проверки совместимости адаптеров не означают свежую сертификацию
всех языков/экспорта/ОС. Kotlin допустим вне BTA-мода; BTA не трогаем.

## Что под что

| Аспект | Язык | Почему |
|---|---|---|
| Игровой тик, симуляция, UI | **C#** | Основной runtime игры — .NET 10; общие правила совместимы с .NET 8 стендов. Единые состояние и команды; лишние выделения памяти исправляются отдельно от выбора языка. |
| Границы правил: вещи, которые обязаны совпадать между игрой и независимым оракулом | **F# (in-process)** | Семь файлов правил перечислены выше. Типизированные вызовы в том же .NET-процессе, без C-ABI/JNI; неизменяемые входы и дифференциальные тесты. Это граница читаемости/проверяемости, не автоматическое ускорение. |
| Следующие кандидаты на F# | — | Мирные бюджеты (`PeaceLedger`/`Cost`), фронтаж-сплит, тактические веса (`CombatTactics.Weights`), логистический trace. Правило, которое можно выписать формулой и проверить перебором, — кандидат. |
| Модовые формулы игроков | **Luau** | Уже есть опциональные мосты/worker; формулы на неизменяемой копии данных — следующий отдельный контракт. Текущий доверенный engine API с прямыми setter-методами не объявляется безопасной песочницей. |
| Инструменты вокруг игры (сборка, анализ, генерация) | **C# / Node (уже есть)** | `Tools/*.mjs` и ps1 доказали подход: ноль SDK, ноль патчей. Kotlin тут возможен, но не нужен: JVM-тулchain ради того, что уже делает один mjs-файл, — лишняя движуха. Kotlin берём, когда появится задача, где реально нужны его библиотеки (например, Kotlin Multiplatform для внешнего companion-приложения), а не «потому что можно». |
| Rust | **можно с 29 октября 2026** (решение автора) | Правило то же, что для остальных: замер, эталонная managed-реализация и тесты на точное совпадение. Прежний замер ownership-ядра не побил C#, поэтому «это же native» само по себе не аргумент. |
| Плотный bulk-числовой код, если профиль появится | **Odin / Nim / Rust** | Только после A/B с упаковкой, валидацией и копированием; выбор по фактическим результатам. С 29 октября Rust больше не исключён. |
| Ежедневная симуляция в отдельном worker или обязательной JVM | **пока не планируется** | IPC, startup, таймауты и синхронизация требуют отдельной приёмки. Сам другой язык/процесс не делает детерминизм невозможным; текущий авторитетный тик остаётся in-process. Это не запрет на проверенный in-process Nim-kernel. |

## Читаемость и модифицируемость — главный выигрыш не от смены языка

Порядок работы с кодом, который даёт больше, чем любой перевод:

1. Горячие проходы — уже переиспользуют буферы на кампании; следующий кандидат
   по профилю — `war:staff` (см. WAR_CALIBRATION_2026_10_26: он же и функционально
   болен — большие войны не кончаются).
2. Правила — выносить в F#-ядра по одному, с дифференциальным тестом против
   C#-реализации (образец: `WarScoreIndexTests`, 12 348 комбинаций).
3. Данные — всё, что моды должны менять, уже в `game/common/**`; новая черта —
   сначала как данные, потом как код, если вообще как код.

## Что это даёт по четырём осям вопроса

- **Производительность**: для F# нет native-marshaling, но остаются цена алгоритма,
  выделений памяти и генерируемого IL. Эквивалентность проверяется отдельно от
  скорости; один .NET runtime сам по себе не доказывает одинаковое время работы.
- **Читаемость**: симуляция на одном языке; правила — декларативным подмножеством
  (F#/JSON), каждое с оракулом.
- **Модифицируемость**: контент в данных, формулы модов — Luau (будущее),
  поведение тика — C# API команд, уже стабилен (`ICampaignCommand`).
- **Ресурсы устройства**: один рантайм вместо трёх; никаких JVM/Kotlin в рантайме;
  деградация графики по профилям (common/performance) уже не про язык.

## Интеграционные шаги ближайших заходов (без Rust)

1. Третье F#-ядро: мирные бюджеты (`PeaceLedger.Cost` + валидация спроса) —
   формулы чистые, оракул строится перебором пакетов; заодно это почва для
   починки «счёт 100 не кончает войну».
2. Четвёртое: веса тактик (`CombatTactics.Weights`) — формула на составе армии,
   дифференциал по сетке входов.
3. Аудит: ни одной новой точке входа в другой язык не разрешается свой поток
   при тике; только чистые функции в том же процессе.
